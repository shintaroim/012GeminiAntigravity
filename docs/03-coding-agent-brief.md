# HON-NEo Webアプリ 実装指示書（Codex／Claude Code向け）
**版:** v0.1  
**用途:** VS CodeでCodex、Claude Code等の開発AIに渡し、リポジトリ内の実装を段階的に進めるための指示書。

---

## 1. 最優先の指示

あなたはHON-NEo独立Webアプリの実装担当AIです。目的は、Gemini Gemに依存せず、HON-NEoの対話型人生編集者体験を専用URLで提供するMVPを構築することです。

まずリポジトリ全体と `AGENTS.md`、`docs/`、`prompts/` を確認してください。既存実装がある場合は、最初に現状を説明し、既存機能を壊さないようにしてください。要件やプロンプトに不足がある場合、推測で思想を変えず、未決事項として記録してください。

### 守るべき原則
1. 要件定義書とシステム設計書を実装判断の基準にする。
2. HON-NEoの元プロンプトを意味的に改変・短縮しない。整理・分割した場合も重要ルールを落とさない。
3. 本人の発言原文、AIの観察、AIの仮説、本人が否定した解釈、本人の承認内容を区別する。
4. AIが利用者の人生や価値観を断定しない。
5. AI APIキー、システムプロンプト、内部状態をブラウザに露出しない。
6. 公開URLで誰でも利用できる前提なので、レート制限と利用量上限を必ず設ける。
7. 1回の作業で大規模な変更を一気に行わず、段階ごとにテストする。
8. 仕様が決まっていない外部サービスを勝手に確定しない。必要な場合はインターフェースと設定値で抽象化する。

---

## 2. 最初に行う作業

コードを書く前に次を行う。
1. リポジトリのファイル構成、依存関係、既存のテストを確認する。
2. `docs/01-requirements.md` と `docs/02-system-design.md` を読む。
3. `docs/source-prompt-v1.0.md` が存在するか確認する。存在しなければ、実装前に元プロンプトをリポジトリへ保存する必要があると報告する。
4. 実装計画を5〜10個の小さなタスクに分解する。
5. 重要な不明点は `docs/decisions/` にADR形式で記録する。
6. その後、最初のタスクだけ実装する。

## 3. 推奨する開発フェーズ

### Phase 0 — 開発基盤
- Next.js App Router + TypeScriptを初期化する。
- ESLint、型チェック、フォーマッター、テストランナーを設定する。
- `.env.example`、`README.md`、`AGENTS.md`を整備する。
- 秘密情報がGitへ入らないことを確認する。

**完了条件:** `npm run dev`、型チェック、lint、テストが動作する。

### Phase 1 — ブランドページとチャットUI
- HON-NEoのブランドトップを作る。
- チャット画面を作る。
- 初回導入文、会話表示、送信中表示、エラー表示、再試行を実装する。
- モバイル画面を優先して確認する。
- まだ本番AI APIがなくても、モック応答でUIをテストできるようにする。

**完了条件:** モックAIで一連のチャット操作を試せる。

### Phase 2 — セッションとDB
- `sessions`、`messages`、`usage_events`を作成する。
- セッション作成、メッセージ保存、会話再開を実装する。
- セッション再開用トークンを安全に生成し、DBにはハッシュを保存する。
- UUIDだけで他人のセッションへアクセスできないことをテストする。
- セッション削除を実装する。

**完了条件:** ブラウザ再読み込み後も本人のセッションを再開でき、他セッションにはアクセスできない。

### Phase 3 — AIプロバイダーとプロンプト
- `AIProvider`インターフェースを作る。
- 初期プロバイダー実装を追加する。
- APIキーとモデル名はサーバー環境変数から読む。
- プロンプトはサーバー側のMarkdownから読み込む。
- API呼び出し失敗時、入力メッセージを失わないようにする。
- 開発時はモックプロバイダーを使えるようにする。

**完了条件:** APIキーをクライアントへ露出せず、実際のモデルで会話できる。

### Phase 4 — 状態管理
- `phase`、`turnCount`、`verbatimQuotes`、`episodes`、`valueHypotheses`、`rejectedWords`、`unresolvedItems`、`storyCandidates`、`compassCandidates`、承認済み成果物を管理する。
- まず最小の `state_json` で実装し、データアクセス層を通じて読み書きする。
- AIが生成した状態更新はスキーマ検証する。
- 本人が否定した語句を再び押し付けないため、`rejectedWords`をコンテキストに含める。
- 原文引用には元のユーザーメッセージIDを紐づける。

**完了条件:** 会話をまたいで状態が保持され、原文・仮説・承認が混同されない。

### Phase 5 — プログラム進行
- `ほんね`、`たたき台をまとめて`、`整える`、`BOOK SEEDをまとめて`、`まとめて`、`今どんな感じ？`を認識する。
- 段階に応じたプロンプトモジュールを読み込む。
- 話す／寝かせる／整える／BOOK SEEDの各ルールを実装する。
- 7 STORIES、3 COMPASS、人生の再定義文は利用者が選択・修正・承認する。
- AI側で自動的に「完成」と決めない。

**完了条件:** コマンドと段階に応じて正しい挙動になる。

### Phase 6 — 保存・エクスポート
- まとめログをコピーできるようにする。
- たたき台とBOOK SEEDをMarkdownとしてコピー／ダウンロードできるようにする。
- BOOK SEEDに未承認の仮説を確定事項として混ぜない。
- 「次のタネ箱」に重要だが選ばれなかった候補を残せるようにする。

**完了条件:** 利用者が自分の成果物を手元に保存できる。

### Phase 7 — 公開準備
- レート制限、入力文字数上限、出力トークン上限、セッション利用量上限を設定する。
- API利用量・処理時間・エラーを本文を記録せずに計測する。
- プライバシー案内、データ削除、保存期間を確認する。
- セキュリティとプロンプト回帰テストを実行する。
- ステージング環境で小規模な試用を行う。

**完了条件:** 公開URLから利用でき、利用量制限とプライバシー上の説明が整っている。

## 4. 元プロンプトを実装へ移すルール

元プロンプトを `docs/source-prompt-v1.0.md` に全文保存し、改変せず参照できるようにする。実行時に読み込むファイルは機能別に分割してよいが、次の内容を落とさない。

- AIは対話型人生編集者・インタビュアーである。
- 7 STORIESは社会的にすごい実績ではなく、今の本人をつくった物語である。
- 3 COMPASSは一般的な価値観診断ではなく、物語を横断して見える本人固有の選択基準である。
- 本音は唯一絶対の正解ではなく「今の私が、自分で選んだ、今の答え」である。
- 人生のハンドルは本人が握る。
- 原文を保持し、AIの言い換えを本人の発言として扱わない。
- 1ターン1問を基本とする。
- 反証を探し、利用者が否定した解釈を再提示しない。
- 「話す」では候補を出し切り、早期に7つと3つを決めない。
- 「寝かせる」では深掘りを急がない。
- 「整える」では利用者の気づきや違和感を最初に確認する。
- BOOK SEEDは本人が承認した成果物をまとめる。
- 出版手続き・章立て・本文執筆を30日プログラム内で行わない。
- 強い苦痛がある場合は深掘りを止め、安全を優先する。

元プロンプトと実行用モジュールの差分を確認するチェックリストを作ること。

## 5. コーディング規約

- TypeScriptのstrict設定を有効にする。
- `any`の安易な使用を避ける。
- 入力データは境界でスキーマ検証する。
- DBアクセスをUIコンポーネントへ直接書かない。
- AIプロバイダーの固有型をアプリ全体へ漏らさない。
- APIエラーは利用者向けメッセージと内部ログを分ける。
- セッション秘密情報、APIキー、会話本文を通常ログへ出さない。
- 重要なロジックには単体テストを書く。
- 仕様変更時はドキュメントとテストを同時に更新する。
- 依存パッケージを追加する前に、既存機能で代替できないか確認する。

---

## 6. 必須テストケース

1. 初回会話で「どんな本を書きたいですか？」から始めない。
2. 1ターンの応答に複数の質問を詰め込まない。
3. 「自由」などの価値観候補を根拠なく断定しない。
4. 本人の原文を正確に保持する。
5. AIの仮説を本人の発言として出力しない。
6. 利用者が否定した言葉を、言い換えて押し付けない。
7. 価値観候補に反する経験も探索対象にできる。
8. 痛みのある経験をポジティブに脚色しない。
9. 出版・章立て・本文執筆へ誘導しない。
10. BOOK SEEDへ未承認内容を確定事項として含めない。
11. APIキーをブラウザ側へ露出しない。
12. セッションIDだけでは他人の会話を読めない。
13. レート制限が機能する。
14. 削除したセッションを通常APIから取得できない。
15. API障害時に入力内容が失われない。
16. Markdownエクスポートが日本語を含め正しく出力される。

## 7. 作業完了時の報告フォーマット

各フェーズの完了時、次の形式で報告する。

- **実装した内容**
- **変更したファイル**
- **実行したテストと結果**
- **残っている課題**
- **仕様確認が必要な点**
- **次に行うべき最小タスク**

テストを実行していない場合、「テスト済み」と記載しない。実装していない機能を実装済みと説明しない。
